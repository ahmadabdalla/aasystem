# Evaluation

Own experiment design and the adoption recommendation. Structural validity, instruction use, and correct work are separate claims. Follow the shared [delegation](../references/execution.md#delegation) and [review-context](../references/execution.md#review-context) rules for capability, invocation, model choice, and isolation limits.

1. **Frame.** Name the behavior under assessment; write three to six observable criteria for the judge only. Include a realistic task and a boundary case. Improvement claims require the prior version under comparable conditions.
2. **Prepare.** Give each candidate a separate working directory, the same organic user request, authoritative project inputs, and its assigned instruction version. Use neutral project names and labels. Hide experiment framing, scoring criteria, expected answers, model names, and other candidates; preserve facts and constraints the task needs. Do not ask candidates to enumerate applied skills. Explicitly requesting a skill tests explicit use, not discovery.
3. **Run.** Dispatch independent fresh candidates under the shared rules. Retain prompts, instruction identities, environments, outputs, permitted transcripts, failures, and artifact identities. Use only available models and access; disclose unavailable capabilities.
4. **Judge.** An independent judge receives the rubric and neutrally labeled outputs, blind to variant and model identity. Score compared variants together on one scale. Inspect actual artifacts and permitted records of reads and actions; run meaningful output checks. Self-reported compliance cannot establish routing or handoffs; unavailable observations remain unverified.
5. **Reconcile.** Read every output and check disagreements against evidence. Distinguish instruction defects, host limits, and fixture faults. Preserve unsuccessful attempts; explain reruns. Recommend adoption, correction, or further investigation within the exercised scope, recording evidence locations and limitations in the existing change record. Rerun affected cases after corrections.

**Retention.** Experiments, materialized fixtures, and run evidence stay outside maintained source by default, using [project evidence conventions](../../bootstrap-verification/references/project-contract.md#evidence-and-retention) through review. Retain a permanent regression case only after demonstrated reuse, with a specific failure to catch and a runnable request and check. Retire obsolete cases; Git preserves committed history. Durable conclusions follow the linked evidence contract.
