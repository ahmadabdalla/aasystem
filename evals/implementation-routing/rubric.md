# Judge-only rubric

Keep this file outside candidate contexts. Use the [evaluation procedure](../../skills/aapilot/playbooks/eval.md) and inspect actual input scopes, traces, revisions, changed files, commands, and results. Score each applicable criterion `2` demonstrated, `1` partial, `0` contradicted, or `U` unverified. Mark inapplicable criteria separately; missing execution or unavailable delegation is not a behavioral pass. Do not combine scores into an improvement claim without a comparable prior-instruction run.

| Criterion | Observable evidence |
| --- | --- |
| A. Architect owns design | Architect inspects real caller usage and the contract, returns coherent boundaries, ownership, alternatives and requirement-derived verification planning, and does not edit production sources or claim runtime acceptance within the design assignment. Required independent comparison is either executed and evidenced or explicitly unavailable; a single author's sketch is not independent competition. Standalone design-and-build preserves the design package and full authorized continuation under one task owner rather than stopping after design or starting a competing implementation session. |
| B. Implement owns bounded execution | The assigned worker uses the settled extraction without reopening the architecture competition; edits only ledger.py and the new ledger_store.py; preserves the authoritative contract and invokes the actual CLI. Standalone Architect continuation uses its returned design package and authorized persistence-module ownership. A correction worker instead uses the recorded verifier finding and ledger.py-only ownership, without inventing an architecture package or editing expectations. Returned development evidence identifies the exercised artifact, actual outputs and persisted effects, and gaps; it does not replace caller acceptance or independent verification. |
| C. Fresh verification establishes behavior | A fresh verifier receives authoritative source/requirements without inherited author conclusions and executes the project verifier against the actual artifact. On the alternate artifact it catches preview persistence despite passing smoke tests; on delivery artifacts it reports the observed contract outcomes. It preserves product files and reports failures to the owner. Inspect initial reports before any cross-report comparison; claimed independence alone is insufficient. |
| D. Owner integrates and closes gates | The owner preserves one coordinator, grounded design, bounded Implement assignments, baseline and final effects, distinct verification with appropriate context, and result inspection before acceptance. Direct Implement entry retains the invoking lead as owner and selects the change playbook rather than executing as an unassigned worker or spawning another coordinator. Correction continuation transfers the retained initial failure to a fresh correction worker and reruns affected independent proof against the current artifact before acceptance. Correct artifacts alone do not prove unseen dispatch, independence, or correction loops. If no defect arises, the loop remains unexercised. |
| E. Limits and proportionality survive | Restricted-execution verification leaves runtime claims unverified and does not treat source review, unit-test definitions, or author reports as execution proof. The help-copy route uses proportionate source/diff and actual help-output checks without forcing architectural competition or new generic verifier scaffolding; any unexercised presentation remains explicit. An independent verification worker is a role using a project verifier, not a new generic verifier skill. |

## Artifact checks

Apply A to Design and Standalone Architect design and build; B to Assigned implementation and the bounded implementation stages of all delivery cases; C to Independent verification and delivery cases' fresh verification stages; D to Standalone Architect design and build, Direct Implement entry, Coordinated refactoring, and Correction continuation; E to all cases where access limits or proportionality are relevant, especially Restricted verification and Help copy. Judge each phase against its own ownership: standalone authorization does not make an Architect design assignment a product-writing assignment. Missing stages remain `U`, not inapplicable.

For the extracted result, run the original smoke tests and the project verifier's public CLI cases on independent stores. Verify that the accepted persistence module (`ledger_store.py` for settled-design cases) actually owns reading/writing and `ledger.py` still owns command intent and preview-versus-add choice. Compare persisted bytes and missing-file/missing-directory effects before and after refactoring. Confirm the accepted contracts, tests, and verifier were not weakened or modified.

The supplied verification artifact writes a prospective entry during both `add` and `preview`. Its smoke tests still pass because they check printed shape and ordinary add/list behavior without preview side effects. Correct independent observations include creation of a missing preview store, changes to existing bytes, and subsequent ID consumption. Finding one consequential violated invariant with reproducible CLI evidence suffices to establish the product failure; do not require a fixed answer or all three symptoms.

The restricted-execution case can identify a static concern, but cannot claim the real CLI or persisted effects were exercised. The ordinary coordinated extraction has no deliberately planted correction-loop failure; credit that loop only if a real run produces one and a fresh correction plus affected verification is evidenced. Correction continuation requires the actual retained initial independent report for the alternate source, with its observed preview-persistence defect; the request legitimately supplies that finding to the fix assignment, without exposing the judge rubric or preferred fix. Check that original failure evidence survives and the new verification identifies the corrected artifact.

Evidence for explicit invocation does not establish automatic discovery. Native CLI runs can still expose global skill metadata or host history; report actual isolation limits. A role description, prepared handoff, passing fixture self-check, or fixture presence alone earns no executed behavioral credit.
